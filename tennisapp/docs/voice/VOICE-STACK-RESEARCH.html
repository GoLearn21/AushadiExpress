00Verdict

At 100 users the entire monthly voice bill for every option on this page lands between roughly $14 and $165. Price is not the pilot decision. The pilot decision is which vendor hands you the most working audio plumbing for free, because on mobile the plumbing — echo cancellation, jitter buffering, Bluetooth routing, reconnect — is where the weeks go.

Abstract the session, not the socket

Nine surfaces, listed in §08. If you abstract at the "send bytes / get bytes" level you will re-write the app when you switch. Abstract at "start a conversation, get events, answer tool calls".

The finding that changes the arithmetic: speech-to-speech APIs bill audio tokens actually sent, while streaming STT vendors bill connection wall-clock. Client-side mic gating therefore cuts a realtime API's bill by 60–70% and cuts a Deepgram or AssemblyAI bill by exactly nothing. This inverts the usual "pipelines are cheaper" advice at conversational duty cycles. See §04.

01The latency budget

Your instinct of 300–500 ms is close but the published research is tighter and more specific than that, and it is worth knowing precisely because it tells you which components you can afford.

The canonical source is Stivers et al., "Universals and cultural variation in turn-taking in conversation," PNAS 106(26), 2009. Across ten typologically unrelated languages they measured the gap between a yes/no question and its answer and found a modal offset of 0–200 ms, with median gaps by language falling between roughly 0 and 300 ms. pnas.org · primary

The second, less-cited half matters more for product design: gaps beyond roughly 700 ms are systematically read as dispreferred — cross-culturally, a long pause before an answer signals reluctance, disagreement, or trouble. secondary summary of Stivers So a slow agent does not merely feel slow. It reads as evasive.

Practical thresholds

  • <300 ms mouth-to-ear — indistinguishable from an attentive human. Currently unreachable over a mobile network to a cloud model.
  • 300–600 ms — the realistic target. Feels like a slightly deliberate person. This is the band to design for.
  • 600–900 ms — users start talking over the agent, which is why barge-in quality matters more than raw speed in this band.
  • >900 ms — the conversation collapses into walkie-talkie turn-taking and people revert to tapping.

The dominant term is not the model

End-of-turn detection is the largest and most controllable slice. A naive silence-threshold VAD set to 500 ms silence guarantees you cannot beat 500 ms. OpenAI's semantic VAD and Deepgram Flux's model-integrated end-of-turn detection both attack exactly this, by predicting turn-end from content rather than waiting out a timer. If you optimise one thing, optimise this — not your TTS vendor.

OpenAI reported a p95 latency reduction of at least 25% across realtime voice models in July 2026, delivered through improved prompt caching rather than a faster model. trade press, Jul 2026 That is a useful hint about where the time actually sits: re-processing conversation history, not generating.

The hidden cost every table omits

Both OpenAI and Gemini re-bill conversation context on every turn. A Google developer forum thread specifically reports Gemini Live native-audio cost scaling with turn count rather than call duration, because each turn re-charges the accumulated audio context. discuss.ai.google.dev At audio-token rates this compounds fast. OpenAI's mitigation is prompt caching at $0.30/1M for cached audio input on mini — a 33× discount, and the reason their p95 improved 25%. Google's mitigation is contextWindowCompression, a server-side sliding window. Turn both on, day one. Budget 1.5–3× the naive audio-only figure if you do not.

Session lifetime and network loss

  • OpenAI — sessions now run up to 60 minutes (raised from 30). Ephemeral client secrets minted via POST /v1/realtime/client_secrets have a default TTL of about one minute, but that TTL governs the handshake: a session started with the secret continues past its expiry, and one secret can open multiple sessions until it expires. developers.openai.com
  • Gemini — this is where Google is genuinely better engineered. Connection lifetime is capped around 10 minutes, but the API ships explicit session resumption: the server streams SessionResumptionUpdate handles, valid 2 hours after termination, and sends a GoAway message with a timeLeft field before closing. Wi-Fi–to–5G handoff is a first-class supported case. ai.google.dev Without compression, audio-only sessions cap at 15 minutes.
  • Everyone — a dropped WebSocket loses in-flight audio. WebRTC does not: packet-loss concealment, adaptive bitrate and ICE restart all degrade gracefully. This is the single strongest technical argument for the WebRTC transport on a phone.

04Cost model, with the arithmetic shown

Assumptions, stated so you can argue with them

  • 5 minutes per session, 4 sessions per user per month.
  • 100 users → 100 × 4 × 5 = 2,000 minutes/month. 10,000 users → 200,000 minutes/month.
  • Per session: microphone open the full 300 s; agent speaks 90 s (30% duty cycle — a UI-driving assistant speaks in short confirmations, not monologues).
  • ~15 conversational turns; system prompt + tool schemas ~1,200 text tokens.
  • Naive figures exclude context re-billing. The "realistic" column applies the multiplier from §02.

Does the ranking change at scale? Yes — and the reason is not what you expect

On naive numbers the ranking barely moves: Gemini Live is cheapest at both scales, the pipeline is second, OpenAI mini third. Everything within about 1.8×.

On realistic numbers the ranking inverts at scale. The pipeline is the only approach whose cost does not inflate with context re-billing, because its context is text tokens at $0.50/1M rather than audio tokens at $3–32/1M. At 10,000 users Pipeline A becomes the cheapest realistic option by a factor of roughly 1.6–3×.

Mic gating is worth more than vendor choice. Stream audio only while the user is actually speaking (client-side VAD gate) and the input side collapses. Say 100 s of real speech instead of 300 s of open mic:

  • gpt-realtime-2.1-mini: input $0.0300 → $0.0100; session $0.0660 → $0.0460 → $18/mo at 100 users, $1,840/mo at 10,000.
  • Gemini Live: input $0.0225 → $0.0075; session $0.0495 → $0.0345 → $14/mo / $1,380/mo.
  • Pipeline A: no change at all. AssemblyAI bills session duration and Deepgram streaming bills connection time. Gating the mic saves you nothing there.

So the honest summary is: at 100 users nothing matters — the spread is $14 to $165 a month and your time is worth more than the whole line item. At 10,000 users the choice is between a gated speech-to-speech API at roughly $1,400–1,900/mo naive (but exposed to context-cost inflation you must actively manage) and a pipeline at roughly $2,500/mo that is flat, predictable and tunable. Both are fine. Neither is a business risk against 10,000 users. Pick on control, not price.

05KMP and mobile: where the real work is

This is the under-documented part and it is where a solo founder loses a month. Concretely, here is the state of it.

Is there a WebRTC option for KMP? Yes, two — and one is from JetBrains

  • Ktor WebRTC client — Ktor 3.3.0 shipped an experimental multiplatform WebRTC client. Supported targets: JS/Wasm, Android, iOS. Android delegates to Stream's precompiled WebRTC library plus Android media APIs; iOS delegates to the WebRTC SDK for iOS plus AVFoundation. It handles peer connections, data channels and media tracks, including audio tracks from the microphone with configurable echo-cancellation constraints. Signaling is not included — you implement it yourself, and Ktor WebSockets to your existing Ktor backend is the obvious answer. ktor.io
  • webrtc-kmp (shepeliev) — mature community SDK on Maven Central, revision M125, Android/iOS/JS. Caveat: on iOS the WebRTC SDK is not a transitive dependency, so you add it to the iOS project manually via CocoaPods or SPM. github.com/shepeliev/webrtc-kmp

Given you are already a Ktor shop, the Ktor client is the natural first attempt, with webrtc-kmp as the fallback if the experimental API is too thin. WebSocket + raw PCM remains the pragmatic path only if you go with Gemini Live, which offers no WebRTC transport on the Developer API — and then you are hand-building everything WebRTC would have given you.

Capturing and playing PCM behind expect/actual

There are KMP audio libraries (kmp-audio-recorder-player, kmp-record) but they are built for file-based record-then-play, not for streaming raw PCM frames with low latency. klibs.io, GitHub For a voice agent you will write the expect/actual yourself. It is perhaps 400 lines per platform. The gotchas:

Sample-rate conversion — the number-one time sink

  • OpenAI demands 24 kHz PCM16 mono little-endian and nothing else. Gemini wants 16 kHz in / 24 kHz out. Nova Sonic resamples to 16 kHz. Device hardware runs at 44.1 or 48 kHz.
  • On iOS, AVAudioSession.setPreferredSampleRate() is a request. The system may ignore it. Always read AVAudioEngine.inputNode.inputFormat(forBus:) at runtime and convert with AVAudioConverter — never hardcode.
  • Connecting a Bluetooth headset can force the session to 8 or 16 kHz mid-conversation and fire a route-change notification. Your resampler must be reconfigurable at runtime, not set up once at session start.
  • On Android, AudioRecord at exactly 16 or 24 kHz is not guaranteed on all devices; query getMinBufferSize and be prepared to capture at 48 kHz and downsample yourself.

Audio session configuration

  • iOS: category .playAndRecord, mode .voiceChat, options .allowBluetooth + .defaultToSpeaker. Setting .voiceChat engages Apple's Voice Processing I/O unit, which gives you AEC, automatic gain control and noise suppression for free. Alternatively, from iOS 13, setVoiceProcessingEnabled(true) on the engine's input and output nodes. secondary
  • Android: capture with MediaRecorder.AudioSource.VOICE_COMMUNICATION, which routes you through the OEM's voice pre-processing chain, and set AudioManager.MODE_IN_COMMUNICATION. Play back with an AudioTrack whose usage is USAGE_VOICE_COMMUNICATION. Request audio focus; release it properly or you break the user's music.

Acoustic echo cancellation: who provides it, and what breaks without it

What breaks: without AEC the microphone picks up the agent's own speech from the loudspeaker. Server-side VAD then fires on the agent's own voice, which the model interprets as the user barging in. It stops speaking, listens to itself, transcribes its own output as user input, and responds to it. The failure mode is not degraded audio — it is a self-interruption loop that makes the feature unusable on speakerphone. On headphones it never reproduces, which is exactly why it survives to production.

Who provides it:

  • iOS — the OS does it well. .voiceChat mode engages the system AEC and it is reliably good across devices. secondary
  • Android — android.media.audiofx.AcousticEchoCanceler is a thin wrapper over the OEM's implementation, and its quality varies enormously by device and Android version. isAvailable() returning true tells you very little. Because of this, most production voice apps bypass the platform AEC and run WebRTC AEC3 directly (or via an SDK), accepting higher CPU for consistent behaviour across the fragmented device fleet. secondary, multiple
  • The SDK — if you take the WebRTC transport (Ktor or webrtc-kmp), AEC3 comes with the media stack and this problem is largely solved for you on both platforms. That is the strongest practical argument for WebRTC over raw WebSocket PCM on mobile.
Fallback if AEC is unavailable

Half-duplex gating: mute the mic while the agent is speaking. It works, and it kills barge-in — the single behaviour that makes voice feel alive. Treat it as a device-specific degradation, detected at runtime, not as a design.

Bluetooth and speakerphone

  • Android 17+ changed this: the audio framework now manages SCO routing rather than the Bluetooth stack, and the stack requests SCO via AudioManager.setCommunicationDevice(AudioDeviceInfo). source.android.com Older code that called startBluetoothSco() needs revisiting.
  • SCO link establishment can take 5–8 seconds on some OEM devices (Xiaomi, OPPO are named), which users read as your app being broken. Fall back to the built-in speaker after ~8 seconds. secondary
  • Missing BLUETOOTH_CONNECT is a silent, OEM-dependent failure. Gate Bluetooth UI on the grant and re-enumerate devices after it is accepted.
  • Keeping AudioManager state and the WebRTC AudioDeviceModule state in two places produces ghost echo and half-muted audio. Keep one source of truth and propagate it to both.
  • iOS — subscribe to AVAudioSession.routeChangeNotification. Headphone unplug, AirPods connect and a call arriving all change the route mid-utterance and may change the sample rate with it.

Network loss mid-utterance

  • WebSocket + PCM: in-flight audio is simply lost. The user finishes a sentence into the void. You must detect the close, reconnect, replay context, and tell the user something happened.
  • WebRTC: packet-loss concealment and adaptive bitrate absorb short drops; ICE restart handles interface changes. Degrades rather than dies.
  • Gemini Live: explicit session resumption with 2-hour handles and a GoAway warning — the best-specified recovery story of any provider, and it partly compensates for the missing WebRTC transport.
  • Product rule regardless of transport: keep the last N seconds of captured audio in a client ring buffer, and on reconnect either replay it or surface "I didn't catch that — say it again." Silence is the worst outcome. The one thing never to do is let a tool call fire from a partially-received utterance.

06The UI-driving pattern

The Zillow behaviour is real but under-documented as engineering. What is confirmed: Zillow's listing-filter functionality was showcased with the Realtime API handling multi-step requests like narrowing listings by lifestyle needs, and OpenAI's openai-realtime-agents open-source demo shows the production-shaped version — tool calls plus control handoff between specialist agents. secondary; OpenAI announcement + coverage I found no detailed public engineering write-up of the Zillow implementation itself. searched, not found

The mechanism, stated plainly

There is no special API. The model emits an ordinary function call mid-conversation; your client executes it as a UI mutation rather than a data fetch, returns a compact result, and the model keeps talking. The whole trick is that the tool's side effect is navigation.

// Tools are the app's verbs, expressed for a stranger.
tool "show_matches"      { skill: "3.0-3.5", radius_km: 10, when: "weeknight_evenings" }
tool "open_player"       { player_id: "..." }
tool "propose_match"     { player_id: "...", court_id: "...", start: "2026-09-02T18:30" }
tool "refine_filter"     { patch: { radius_km: 25 } }   // patch, never full replace
tool "undo_last_action"  { }                            // non-negotiable, see below

// Result payloads stay tiny. The model narrates; it does not read the list aloud.
→ { count: 7, top: ["Priya 3.5", "Marcus 3.0"], applied: { radius_km: 25 } }

The four known design problems, and what to do

1. Latency between speech and UI update

The UI update lands after end-of-turn detection plus model round-trip — 500–800 ms after the user stops speaking. That is fine for a screen change but wrong for a filter slider, which the user expects to move as they speak. Mitigation: render an optimistic pending state the moment a tool call begins streaming (a shimmer on the affected filter chip), and commit on the result. Never animate a full re-layout on speculation.

2. Showing what the model heard

Non-negotiable, and the most common omission. Users cannot debug a voice interface they cannot see. Show the live input transcript — this is where AssemblyAI's immutable transcripts pay for themselves, because mutable partials visibly rewrite themselves on screen and read as the app being confused. If your provider only emits mutable partials, render them at reduced opacity until finalised so the rewriting reads as intentional.

3. UI thrashing on every utterance

Three defences. (a) Make tools patches, not full-state replacements, so "actually make it 25 km" adjusts one field instead of rebuilding the query. (b) Debounce commits — hold a tool call ~150 ms and coalesce if another arrives, since the model often emits two in quick succession. (c) Separate filter tools (cheap, animate freely) from navigation tools (expensive, require a settled turn). Never let a navigation tool fire from a partial transcript.

4. The user verbally contradicts a tool call

"Show me players near Kensington — no wait, Hackney." The Kensington call has already fired. Three things make this survivable:

  • A first-class undo_last_action tool, and a client action stack the model can actually reach. Without it the model will apologise and issue a new filter, leaving stale state underneath.
  • Every UI-mutating tool must be idempotent and reversible. Design the app state as a reducer over an action log, which Compose Multiplatform suits well.
  • Semantic VAD helps materially here — it waits through "no wait" instead of treating the pause as end-of-turn, so the contradicting call often never fires.

Prior art worth reading

AG-UI (Agent User Interaction Protocol) is the only serious attempt at standardising this: an event and state protocol defining how UI updates, agent state and user interactions flow while the agent is working. docs.ag-ui.com You almost certainly should not adopt it for one app, but its event taxonomy is the best available checklist of the cases you will hit. The recurring theme across the generative-UI literature is the same one: agents emit two data streams at once — structured (tool calls, state deltas) and unstructured (speech, text) — and interfaces designed for request/response have no pattern for showing an unsolicited action or explaining why it happened.

07Store review, privacy and recording law

Always-listening and background audio

  • A foreground, user-initiated, visibly-indicated voice session is unremarkable to both stores. Nothing here is a review risk if the mic runs only while a session is on screen with a visible active-listening indicator. Do that and skip most of this section.
  • iOS background audio is where apps get rejected. Apple rejects apps that declare audio in UIBackgroundModes but cannot play audible content in the background; the capability is expected to correspond to a real, user-visible audio feature reachable from main navigation. Apps recording in the background have been rejected on appeal when the use case did not justify it. developer forums + rejection guides A tennis matchmaking app almost certainly cannot justify background mic. Do not ask for it.
  • Android requires a foreground service with foregroundServiceType="microphone" and, since Android 14, that type declared and permitted or startForeground throws. Plus a persistent notification.
  • Permissions: iOS NSMicrophoneUsageDescription is mandatory and its wording is read by reviewers — say the audio is sent to an AI service to run the conversation. Android needs runtime RECORD_AUDIO, plus BLUETOOTH_CONNECT for headsets.
  • Wake words are a different product. A hotword detector implies a genuinely always-on mic and invites scrutiny on both stores. Use a button.

Privacy disclosure

  • Google Play Data Safety: "Audio files" explicitly covers voice or sound recordings. You must declare collection and sharing, and Google is explicit that data handled by third-party SDKs and backends counts as yours to declare — streaming audio to OpenAI or Google is sharing, not merely collection. developer.android.com, support.google.com
  • Apple App Privacy label: declare Audio Data, and declare it as linked to the user if sessions are tied to an account (they will be, for matchmaking). If any transcript feeds ranking or recommendations, that is a second disclosure.
  • Your privacy policy must name the processor. "A third-party AI provider" is not sufficient under GDPR if you have any EU pilot users.

Two-party consent — take this seriously

This is a live and rapidly worsening area of US litigation, not a theoretical risk.

  • California's Invasion of Privacy Act (CIPA) generally requires all-party consent and carries a private right of action with statutory damages up to $5,000 per violation. CIPA §631 (anti-wiretap) is being applied to cloud AI that processes audio in real time during transmission — which is precisely what a realtime voice API does. law-firm client alerts, 2025–2026
  • The doctrine that should change your vendor contract: courts have found at the pleading stage that if a vendor could use the content to train or improve its own platform, that capability alone supports a CIPA claim — whether or not it did. Goodwin, Fisher Phillips, IAPP, 2025–2026
  • Active matters cited include four class actions against Otter.ai over consent (as of Apr 2026), Cruz v. Fireflies.AI (Illinois BIPA, Dec 2025), Galanter v. Cresta (CIPA, Jun 2025) and Lisota v. Heartland Dental (federal wiretap, Jul 2025). secondary legal press

Your actual exposure is lower than a meeting recorder's, and here is why — protect it. One user talks to a bot about their own tennis availability. There is no second party whose communication is being intercepted. The risk appears the moment a second person's voice can be captured, so: (1) never build a feature where two players talk to the agent together; (2) get explicit in-app consent naming the AI provider before the first session, and log it; (3) negotiate a zero-retention, no-training term with your provider and keep the paper — under the capability doctrine, the contract is the defence; (4) do not persist raw audio, only the transcript you need, and say so.

Accessibility

Voice is an accessibility win for motor-impaired users and an accessibility barrier for Deaf and hard-of-hearing users. Every voice-driven path must have an equivalent tap path — which the tool-call architecture gives you almost free, since the tools are the app's actions. Live captions of the agent's speech are the other half, and they cost nothing when the provider already emits output transcription.

08What the adapter must abstract

Abstracting at the byte level is the trap. Every provider differs in sample rate, framing, event names and turn semantics, and a byte-level adapter leaks all of it. Abstract at the level of a conversation that emits events and asks for tools. Nine surfaces:

// commonMain — the entire contract the app is allowed to know about.

interface VoiceSession {
    val events: Flow<VoiceEvent>
    suspend fun start(config: VoiceConfig)
    suspend fun sendToolResult(callId: String, json: String)
    suspend fun injectContext(text: String)   // 1. out-of-band steering
    suspend fun interrupt()                    // 2. user tapped stop
    suspend fun setMicGate(open: Boolean)      // 3. cost + privacy control
    suspend fun close()
}

sealed interface VoiceEvent {
    // 4. TWO transcripts, always distinguished, always surfaced
    data class UserTranscript(val text: String, val final: Boolean) : VoiceEvent
    data class AgentTranscript(val text: String, val final: Boolean) : VoiceEvent

    // 5. turn state — drives every affordance in the UI
    data class Turn(val who: Speaker, val phase: Phase) : VoiceEvent

    // 6. tool calls: the UI-driving channel
    data class ToolCall(val callId: String, val name: String, val args: String) : VoiceEvent

    // 7. barge-in as an event, not an inference
    object Interrupted : VoiceEvent

    // 8. connection state incl. resumable-vs-fatal distinction
    data class Connection(val state: ConnState, val resumable: Boolean) : VoiceEvent

    // 9. usage, normalised to seconds — never expose vendor token units
    data class Usage(val heardSec: Double, val spokenSec: Double) : VoiceEvent
}

What must live inside the adapter and never leak out

  • Sample rate and framing. The app hands over device-native PCM; the adapter resamples to whatever the provider wants. Nothing above the adapter knows 24 kHz exists.
  • Transport. WebRTC for OpenAI, WebSocket for Gemini, HTTP/2 for Nova. The app sees a session, not a socket.
  • Turn-detection strategy. Server VAD, semantic VAD, Flux end-of-turn — all collapse into Turn events.
  • Tool schema translation. Define tools once in a provider-neutral form; the adapter emits OpenAI-shaped, Gemini-shaped or Bedrock-shaped declarations.
  • Credentials. The adapter asks your Ktor backend for a short-lived token. No provider key ever ships in the app, and swapping providers is a backend change.
  • Reconnection and context replay. Gemini gives you resumption handles; OpenAI does not. The adapter hides the difference behind Connection(resumable=).
  • Session-length caps. 10-minute connections, 15-minute uncompressed audio sessions, 60-minute session ceilings. The app must never see these.

What deliberately stays outside

The tool implementations and the action stack are app code, not adapter code. They are your product. If they end up inside the adapter you have built a framework instead of a swap.

Build the second adapter before you need it. Implement OpenAI first, then implement Gemini Live as a stub that runs your integration tests. It will take a day and it is the only way to know the interface is actually provider-neutral rather than an OpenAI wrapper with different names. Every abstraction written against one implementation is a wrapper.
