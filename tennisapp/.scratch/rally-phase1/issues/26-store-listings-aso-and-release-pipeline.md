# 26: Store listings, discoverability, and the release pipeline

**What to build:** Both store listings exist as reviewed files in the repository — title, subtitle, keywords, descriptions, category, age rating, screenshots — and are pushed to the consoles by Fastlane from the Mac, so the ADR-001 promise in the listing cannot drift from the product. Screenshots are generated by Playwright from the running web app at device viewports. TestFlight and the Play internal track are one command each. Store "What's New" text is the release-notes number, not marketing copy.

**Blocked by:** 24, 25

**Status:** ready-for-agent

- [ ] `store/listing/en-US/` holds every listing field for both stores within each store's character limits; a test asserts the limits and that the subtitle/short description is the ADR-001 promise verbatim
- [ ] Screenshots for the required device sizes are produced by a Playwright script from seeded fixture data and committed; re-running the script reproduces them byte-for-byte except timestamps
- [ ] Icon and Play feature graphic exported from the design tokens at the required sizes, Apple icon without alpha
- [ ] `fastlane ios beta` uploads to TestFlight and `fastlane android internal` to the Play internal track from the Mac with credentials in the keychain only; the lanes are documented in `store/README.md`
- [ ] Release notes entry produces the "What's New" text for both stores through the same lane
- [ ] Both listings are US-only at first release, category Sports, adults-only age declaration consistent with the PRD
- [ ] A listing-review checklist (privacy URL, demo account, permissions rationale, screenshots current) is a file and is ticked in the PR that submits each release
